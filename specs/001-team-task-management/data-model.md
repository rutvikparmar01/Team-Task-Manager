# Phase 1 Data Model: Team Task Management

Derived from `spec.md` Key Entities, with the Phase 0 default for team-member assignment applied
(see `research.md` item 7 — **not yet confirmed by the user**).

## Project

Represents a named container for related work (spec FR-001–FR-003).

| Field | Type | Rules |
|---|---|---|
| `id` | string (Mongo ObjectId) | Generated by the database |
| `name` | string | Required; trimmed; rejected if empty/whitespace-only (FR-002) |
| `description` | string | Optional |
| `createdAt` | ISO date-time | Set on creation; not user-editable |

**Relationships**: A Project has zero or more Tasks (one-to-many, via `Task.projectId`).

**Notes**: Project names are not required to be unique (spec Edge Cases). There is no update or
delete operation on a Project in this version (spec Assumptions).

## Task

Represents a unit of work belonging to exactly one project (spec FR-004–FR-012).

| Field | Type | Rules |
|---|---|---|
| `id` | string (Mongo ObjectId) | Generated by the database |
| `projectId` | string (ObjectId ref → Project) | Required; must reference an existing project |
| `title` | string | Required; trimmed; rejected if empty/whitespace-only (FR-005) |
| `description` | string | Optional |
| `priority` | enum: `"Low" \| "Medium" \| "High"` | Defaults to `"Medium"` if omitted at creation (FR-010) |
| `status` | enum: `"Todo" \| "In Progress" \| "Done"` | Defaults to `"Todo"` at creation (FR-011); changeable to any of the three values in any direction (FR-012) |
| `assigneeId` | string (ObjectId ref → TeamMember) \| null | Optional; a task may remain unassigned (FR-008) |
| `createdAt` | ISO date-time | Set on creation; not user-editable |

**State transitions**: `status` may move freely between `Todo`, `In Progress`, and `Done` in any
direction, including moving "backward" (spec User Story 3, Acceptance Scenario 4). Setting status
to its current value is a no-op, not an error (spec User Story 3, Acceptance Scenario 3).

**Relationships**: Belongs to exactly one Project. Optionally references one TeamMember.

**Notes**: Editing `title`/`description` after creation, and deleting a Task, are out of scope for
this version (spec Assumptions) — only `status`, `priority`, and `assigneeId` are mutable after
creation.

## TeamMember

Represents a named person who can be assigned to tasks (spec Key Entities; default assignment
model from `research.md` item 7 — **pending user confirmation**).

| Field | Type | Rules |
|---|---|---|
| `id` | string (Mongo ObjectId) | Generated by the database |
| `name` | string | Required; trimmed; rejected if empty/whitespace-only |
| `createdAt` | ISO date-time | Set on creation |

**Relationships**: Zero or more Tasks may reference a TeamMember via `Task.assigneeId`.

**Notes**: No credentials, login, or permission fields — a TeamMember exists solely to label task
ownership (spec Assumptions). Duplicate names are allowed (no uniqueness constraint), consistent
with the demo-scale, no-auth nature of the app.

## Derived view: Project Progress

Not a stored entity — computed from a project's tasks (spec FR-015–FR-016):

- `totalTasks`: count of Tasks where `projectId` matches.
- `doneTasks`: count of those Tasks where `status === "Done"`.
- `progress`: `doneTasks / totalTasks` when `totalTasks > 0`; an explicit "no tasks yet" state
  when `totalTasks === 0` (never a numeric value implying completion of an empty project).
